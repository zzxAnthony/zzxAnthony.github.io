UniFormer：从组件扩容到统一模型扩容

推荐模型真正的扩容，不只是把某个 Transformer 堆得更深，而是重新组织 feature space 与 task space。

论文精读2026.07.2812 MIN READ

问题：组件级扩容为什么不够？

工业精排模型通常由行为序列建模、非序列特征交叉和多任务预估组成。过去的扩容大多发生在某一个模块：序列侧加长历史，交叉侧增加层数，多任务侧增加 expert。但系统的真实建模空间并不是这些模块的简单拼接。

Embedding / Tokenization
→ Sequence Modeling
→ Feature Interaction
→ Multi-task Learning
→ Prediction Heads

只扩一个组件会让容量分配失衡。更关键的是，很多联合模型只统一了 feature space，点击、时长、点赞等任务仍然停留在末端 tower 中。

核心：两阶段统一交互

UniFormer 的关键判断是：先让序列行为与非序列特征在 feature space 中充分融合，再让 task token 主动读取高阶特征，并显式建模任务关系。

把工业推荐排序从 component-centric scaling 推向 model-centric co-scaling，并把 task space 作为一等公民。

这让任务不再只是被动接收共享表示的输出头，而成为统一交互空间里的查询者。模型容量也因此能在特征理解与目标区分之间更自然地流动。

工程上的三个启示

  1. 先定义扩容坐标。 参数量不是唯一尺度，应分别观察序列、特征和任务三个维度的瓶颈。
  2. 任务冲突需要结构化处理。 共享底座越强，越需要让任务保留独立读取与交互的能力。
  3. 统一不等于完全共享。 合理的 token 设计和交互边界，往往比简单堆叠层数更重要。

我的判断

UniFormer 最值得关注的不是某个局部模块，而是它重新定义了推荐模型“应该在哪里扩容”。当序列长度、特征数量和业务目标都继续增长时，统一空间中的容量协同会比单点放大更重要。
